# 公開申込の冪等性：ローカルDBテスト

対象は `20261019_add_registration_idempotency.sql`。既存Supabaseへの自動適用は行わない。

マイグレーションは `postgres` ロールで適用する前提とする。新しいスキーマ・テーブル・SECURITY DEFINER関数の所有者も `postgres` になる。隔離DBテストも同ロールで適用する。既存ローカルSupabaseへの適用は別途指示を受けるまで行わない。

## 実行方法

Dockerに `ghcr.io/supabase/postgres:17.11.0.004` がローカル保存されている環境で実行する。

```sh
SHINSEIKAI_IDEMPOTENCY_DB_TEST=1 node --test tests/idempotent-registration-db.test.mjs
```

全テストと同時に実行する場合：

```sh
SHINSEIKAI_IDEMPOTENCY_DB_TEST=1 node --test tests/*.test.mjs
```

フラグなしの通常実行では、このDBテストだけを明示的にスキップする。テストは毎回、新しい隔離コンテナ内で基準・参加申込管理・冪等性の3マイグレーションを適用する。既存のローカルDBをリセットしない。

- ネットワークなし、ホストポートなし、ホストディレクトリのマウントなし。
- DBはUTF-8、PostgreSQL 17。データは一時ファイルシステム内のみ。
- `.env`、Supabase CLIの接続先、リモートDBは使用しない。
- 終了時に自分が作成したコンテナだけを停止し、自動破棄する。
- 強制終了で片付けが中断した場合は、`shinseikai-idempotency-test-` で始まる該当コンテナのみを確認する。

業務エラーの回帰テストでは、既存の `submit_registration` を実行し、内部RPCから伝播する6種類のSQLSTATEとメッセージを固定の期待値と照合する。同じ条件で冪等性ラッパーの結果コード・HTTPステータス・再送結果・台帳件数・申込件数も確認する。既存RPCのSQLSTATEやメッセージを変更すると、ラッパー側も同時に変更した場合を含めて、この契約テストは失敗する。既存RPCとラッパーを合わせて変更する際も、契約変更のレビューが必要になる。

## 新RPCの契約

`submit_registration_idempotent(uuid, bigint, text, text, text, bigint[])` は service_role のみ実行可能。

- 成功は `{"success":true,"code":"REGISTERED","http_status":201}`。
- 確定した業務エラーも同じキーに記録し、`success:false` と安全なコード・HTTPステータスを返す。
- 同一入力の再送は同じ結果を返す。後で満員・受付停止・取消となっても登録を繰り返さない。
- 同じキーで別の有効な入力を送ると SQLSTATE `PT409`。
- 完了から30×24時間以上は SQLSTATE `PT410`。詳細結果を返さず、キーを再利用しない。
- 不正なキー・氏名等の形式・空配列・配列重複は、キー確保前に `22023` で拒否する。
- 業務エラーのJSON応答はDB上は正常終了し、その記録をコミットする必要がある。将来のAPIは `http_status` をHTTP応答へ変換すること。
- 予期しないエラーは例外を再送出し、キー・申込・明細をすべてロールバックする。

## 個人情報と保存

台帳に氏名・連絡先・備考や入力JSONを保存しない。入力はDB内で正規化し、専用の秘密鍵によるHMAC-SHA-256で比較する。キーと操作名も指紋に含める。

秘密鍵と台帳は `registration_private` スキーマに置く。RLSを有効化し、匿名・一般認証・service_roleにも直接操作権限を付与しない。所有者権限で動く新RPCだけがアクセスする。

現在の秘密鍵は、少なくとも照合期間中は変更しない。鍵のローテーション・結果の物理削除を行う場合は、旧キー照合と使用済みキーの保持を別途設計する。今回は台帳を削除する処理・ジョブを追加していない。30日後も台帳は残り、関数が返す内容だけを制限する。

`pgcrypto` が `extensions` スキーマにあることを前提とする。未導入なら同スキーマへ追加する。別スキーマに既存導入されている場合は、勝手に移動せずマイグレーション全体を失敗させる。

既存の登録RPC・管理者RPCは変更しない。公開フォーム・公開POST API・Bot対策・レート制限は今回の対象外。冪等性キーは大量申込対策の代わりにはならない。

## 受付完了メール（20261102、初期無効）

`20261102_add_registration_created_new.sql` は既存関数1つのJSONへ `created_new` を追加する。
引数・jsonb型・ロック・定員・エラー・要求記録は不変。新規成功だけtrue、再確認・不成立はfalse。
旧3キー応答は引き続き受理するが、メールは送らない。4キー応答はサーバーで厳密に検査し、
公開APIの201・success/code/messageへ追加フィールドを漏らさない。

### 配送の制約

- 送信は新規成功の応答を受け取ったAPI呼び出しだけ。電話等の連絡先は送信対象外。
- 匿名権限で対象開催回と最大50クラスを2リクエストで取得する。会場・日時等は取得時点の情報。
- メタデータ取得からResend受理まで合計3秒で打ち切る。失敗・中断でも申込成功を返し再送しない。
- DBコミット後の通信断/プロセス終了/メール失敗は未送信になり得る。再確認では補完しない。
- Resendキーは `preview/registration-confirmation/{申込キー}`。Resendの重複防止保持は24時間。
- 新しい申込キーによる同内容の別申込は別メール対象。受理成功は受信箱到着の保証ではない。
- 備考・申込キー・クラスIDなどは本文に含めず、メール本文/プロバイダー応答をログ出力しない。

### 切り戻し

メール無効化 → 保管した旧関数定義へ戻す（所有者/ACLも照合）→ 必要なら旧アプリへ戻す。
旧アプリは4キーRPC応答を拒否するため、新関数のまま旧アプリへ戻してはいけない。
既存申込・要求記録は削除しない。送信済みメールをDB切り戻しで取り消すことはできない。
